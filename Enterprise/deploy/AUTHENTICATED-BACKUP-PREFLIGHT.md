# Authenticated backup identity preflight (PR-004 / LAN-05 / LAN-08)

Reference offline contract layered on #103. A detached raw 64-byte Ed25519 signature covers the exact canonical UTF-8 JSON manifest, including source installation UUID, backup UUID, creation timestamp, declared format, bounded size and SHA-256 of the opaque backup payload. The trusted public key, SHA-256 of its DER SubjectPublicKeyInfo and expected source installation UUID must be obtained independently from the authenticated recovery record. Never accept a trust anchor or claimed signer pin from the backup itself. No private key is handled by the verifier. The synthetic test suite creates throwaway keypairs only.

Reject unknown schemas, duplicate or noncanonical JSON, wrong signer/installation, modified payload, path aliases, oversized input and detected changes during verification. Payload hashing is streamed and bounded by the signed size. A verified manifest supplies the identity to #103's read-only restore planning; clone-new remains blocked. A signed stale backup can still be valid, so timestamp is evidence, not freshness approval. The string encrypted-backup-container is a format declaration, not cryptographic encryption evidence: the result explicitly reports encryption_verified=false and mutation_authorized=false.

This is not integrated with live backup.sh/restore.sh or production storage. Callers must provide trusted locked staging and approved signature key custody/rotation, prevent concurrent writers and reverify the exact bytes consumed at restore. This does not establish actual encryption/decryption, anti-rollback selection, old-host fencing, secure Windows path/ACL handling, database identity or tenant/device rekey. No actual restore, key provisioning, deployment or production acceptance. DEC-001 remains open.
