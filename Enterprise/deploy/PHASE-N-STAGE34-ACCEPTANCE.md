## Purpose and boundary

N32 collected redacted offline/recovered Windows SQLite evidence. N33 verified
a tenant/device/batch-scoped MySQL receipt using a read-only query, but its
portable JSON was unsigned and its origin required external review. N34 adds
an optional Ed25519 signature from an authorized independent operator, binding
the exact original bytes of N32 offline, N32 recovered and N33 server receipt
files. A separately approved full SHA256 fingerprint of the public key's DER
SPKI is MANDATORY. Trusting an attestation-provided key pin would be circular.

The signature proves integrity after signing under the selected key only.
It does NOT independently prove actual network outage, truthful reporting,
MySQL operator authorization, SMTP/webhook delivery, signed public installer
or customer production readiness.

## Implementation

- Enterprise/deploy/stage34-attestation-core.mjs validates the exact source
  file hashes, batch ID, case ID, queue lifetime fingerprint, event count,
  local ACK, receipt count and all false production/external approval flags,
  then builds a deterministic signed payload. An operator-supplied Ed25519
  private key signs the canonical JSON. The signed payload forbids a
  production certificate or independently verified physical outage claim.
- Enterprise/deploy/stage34-operator-signature.mjs is an offline sign/verify
  CLI. It creates no keys and never touches a database or network, never
  overwrites an existing report and does not print private key contents.
  On Linux private PEM file mode 0600 or stricter is required. It supports
  vault-provided N34_SIGNING_KEY_PASSPHRASE for encrypted PEM. Verification
  requires a separately supplied public PEM AND approved 64-character SPKI
  fingerprint. Attestation timestamp must not be from the future and
  signatures expire after 90 days.
- Enterprise/tests/New-Stage32CustomerEvidenceBundle.ps1 supports optional
  OperatorAttestationFile, TrustedOperatorPublicKeyFile and
  ApprovedOperatorKeySha256, but only when ServerReceiptReport is supplied.
  It invokes the Node verifier offline before creating a composite bundle.
  A valid signature adds an attestation hash and approved key fingerprint.
  Source authentication, operator authorization, production signoff and
  actual network-outage verification remain PENDING/false.

## Operator workflow (only after independent approval)

1. Collect real customer N32 offline/recovered evidence after a customer-
   authorized interruption and recovery. Separately capture real network
   outage observation.
2. An independent DBA uses N33 with a SELECT-only, tenant-scoped MySQL
   credential to generate its redacted receipt report. Authenticate that
   operator and the input case mapping out of band. No app/agent secret
   should be included with the evidence files.
3. Security operations approve actual Ed25519 signing key custody, role,
   revocation and rotation policy separately from this repository. A private
   PEM is supported only if its export is approved by the organization's
   security policy; prefer an HSM or controlled signing service as relevant.
   No customer signing keys are provided or generated by these scripts.
4. Review the three exact source files and run the authorized signature:

       node Enterprise/deploy/stage34-operator-signature.mjs sign --offline /secure/n32/stage32-offline.json --recovered /secure/n32/stage32-recovered.json --receipt /secure/n32/stage33-server-receipt.json --private-key /secure/operator-ed25519-private.pem --output /secure/n32/stage34-attestation.json

5. Security operations distributes the approved Ed25519 public PEM and its
   full SHA256 fingerprint of DER SPKI through a trusted channel **separate**
   from the unsigned JSON attestation. Reviewer must not derive approval
   solely from the received report. Verify independently, offline:

       node Enterprise/deploy/stage34-operator-signature.mjs verify --offline /secure/n32/stage32-offline.json --recovered /secure/n32/stage32-recovered.json --receipt /secure/n32/stage33-server-receipt.json --attestation /secure/n32/stage34-attestation.json --trusted-public-key /secure/approved-public.pem --approved-spki-sha256 APPROVED_64_HEX_SPKI_PIN

6. On authorized Windows with Node.js installed, add the signature to a
   NEW redacted N32 bundle. These lines are a single PowerShell command:

       .\Enterprise\tests\New-Stage32CustomerEvidenceBundle.ps1 -EvidenceDirectory C:\Secure\N32Case -BundlePath C:\Secure\N32Case\n34-reviewed-bundle.json -ServerReceiptReport C:\Secure\N32Case\stage33-server-receipt.json -OperatorAttestationFile C:\Secure\N32Case\stage34-attestation.json -TrustedOperatorPublicKeyFile C:\Secure\approved-public.pem -ApprovedOperatorKeySha256 APPROVED_64_HEX_SPKI_PIN

   The resulting JSON reports pinned_operator_signature_verified=true
   while production_certified=false, server_report_source_authenticated=false
   and human_operator_signoff=PENDING. Signing does not confer deployment
   authorization, and a public GitHub release is not created.
7. Separately approve physical Windows NETWORK SERVICE reconnect, Hostinger
   HTTPS/DNS/VPS, real offsite MySQL backup restore, real third-party
   integrations and the approved publisher-signed public MSI.

## CI and acceptance limits

- CI generates ephemeral Ed25519 keys only for synthetic test fixtures.
  Test cases reject key substitution, unexpected claims, wrong approved
  pin, altered source file bytes, tampering, invalid signature, old/future
  timestamp and output overwrites.
- Windows PowerShell composite evidence bundling must verify the pinned
  signature; it must not produce a bundle on wrong pin or changed receipt.
- PR and main CI green is CODE/CI only; it is not a cryptographic claim
  about any real customer's production key or live MySQL/database.
