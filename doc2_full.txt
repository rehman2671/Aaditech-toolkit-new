Part A — Key Improvements Incorporated in This Revision
Listing every backend service individually in the original requirements does not, by itself, mean each one must become a separate microservice. The requirements do explicitly call out queue-based ingestion, stateless APIs, and future horizontal scaling as important architectural properties. The three improvements below make sure a coding agent cannot quietly over-engineer, under-secure, or fake its way past those properties.
A.1  Explicit Service-Topology Decision Gate
Mandate: Before any code is written, the architecture must explicitly choose and justify one of: (a) modular monolith, (b) modular monolith + background workers, or (c) independently deployable microservices. The default assumption, unless dependency analysis proves otherwise, is modular monolith + workers. This decision must be written down as an Architecture Decision Record before Section 5 (Service Boundaries) of Part C is implemented.
Why this was added: The original requirements list many backend domains (device management, metrics ingestion, alerting, MSI builder, etc.) as separate concerns. A coding agent reading that list literally tends to translate "separate concern" into "separate microservice," producing 10–15 independently deployed services for what is still, at this stage, an MVP. That inflates operational complexity, cross-service latency, and deployment surface area without a corresponding benefit, and it works against the requirement for developer productivity and operational simplicity.
Reinforces original section(s): Section 4 (Technology Stack — operational simplicity, developer productivity), Section 5 (Service Boundaries), Section 11 (Queue/Event Architecture), Section 19 (Deployment Architecture).
A.2  MSI Package Builder Treated as a Secure Package-Generation Subsystem
Mandate: The MSI Package Builder must be designed and implemented as a first-class, security-sensitive backend subsystem — with its own build pipeline, signing key protection, artifact storage, download authorization, and audit trail — never as a simple "download the installer" button wired to a static file.
Why this was added: The original directive already states this is a mandatory core feature and explicitly prohibits hard-coding permanent secrets inside MSI packages. Left implicit, a coding agent under time pressure will often implement the path of least resistance: a pre-built installer with a baked-in API key or static enrollment secret. That directly violates the enrollment lifecycle (Section 8) and the no-hard-coded-secrets rule (Rule 9). Calling this out again, explicitly, closes that shortcut.
Reinforces original section(s): Section 14 (MSI Package Builder), Section 8 (Enrollment & Security), Rule 9 (Never hard-code secrets).
A.3  Hard Rule: No Mock Telemetry or Fake Production Data
Mandate: Every metric, inventory item, and event surfaced by the platform must originate from a real collector reading an actual OS API, system interface, or validated library. This is a blocking rule, not a style preference: a build that ships simulated CPU, RAM, disk, or process data for demonstration purposes is not acceptable at any phase, including early MVP demos.
Why this was added: The original document already states "no mock telemetry or fake production data" and requires real endpoint collectors (Section 1, Section 6, Rule 4). Elevating it to a named hard rule in this revision makes sure a coding agent cannot rationalize "just for the demo" fake values as a temporary convenience, since that is exactly the failure mode the original rule was written to prevent.
Reinforces original section(s): Section 1 (Source-of-Truth Rule), Section 6 (Agent Architecture), Rule 4 (Never create fake telemetry).

Part B — Technology Stack Lock: Go Backend Edition
This section amends Section 4 (Technology Stack) of the original directive for the current implementation scope. It does not remove any requirement — it removes the open language choice and replaces it with a locked decision, consistent with Section 4's own instruction to "freeze the technology stack before implementation."
B.1  Language & Runtime Decision
Amendment: Wherever Section 4 of Part C says "Prefer a Python-based backend where technically appropriate," substitute: "The backend is implemented in Go." This is a project-level engineering decision made by the platform owner, not an inference by the implementing agent, and it is now binding for all backend components.
Current phase scope: Backend Core — HTTP/REST API layer, PostgreSQL schema and migrations, and the Authentication / Multi-Tenancy / RBAC foundation described in Section 13 and Phase 1 of Section 22.
Every other selection criterion in Section 4 (production reliability, long-term maintainability, security, performance, horizontal scalability, developer productivity, operational simplicity, availability of mature libraries, enterprise deployment requirements) still applies in full and must be used to choose the specific Go framework, ORM/query layer, migration tool, and supporting libraries. Those specific package choices are not prescribed here; they must be proposed with the same Technology / Version / Purpose / Reason / Alternatives Considered / Why Selected / Operational Impact / Security Impact table that Section 4 already requires, then frozen the same way.
B.2  Consequences for Adjacent Sections
Locking the language does not change any requirement — it constrains how each one is met:
Section 5 — Service Boundaries: Combined with Improvement A.1: module boundaries inside the Go codebase (e.g. internal/devices, internal/metrics, internal/alerts) must be as clean as they would be if each were a separate service, so a later split to independent services is a deployment change, not a rewrite.
Section 7 — Agent ↔ Server Protocol: The wire protocol and message schemas remain language-agnostic (versioned JSON/HTTP contracts as required); Go implements the server side, and the OS agents (Section 6) remain independent native/cross-platform code, not Go-specific.
Section 12 — API Architecture: OpenAPI remains the contract of record; a Go web framework must serve exactly what the OpenAPI spec describes, generated or validated against it, never hand-diverging.
Section 21 — Testing Strategy: Go's standard testing tooling (table-driven tests, race detector, integration tests against a real PostgreSQL instance) satisfies the unit/integration/API-contract/database test categories already required.
Section 23 — Implementation Artifacts: The /backend/ and /database/ artifact directories are Go module(s) and SQL migrations respectively; /contracts/openapi/ and /contracts/agent-protocol/ stay language-neutral.
No other requirement in Part C is weakened, removed, or reinterpreted by this stack lock.
